    Problem

    Hospitals want to know, at discharge, which patients are likely to bounce back within 30 days — it's a quality metric, a cost driver, and in the US a source of Medicare penalties. The modeling problem is well-trodden. The systems problem is not: most ML portfolios stop at a notebook with a cross-validated AUC. What does the whole thing look like — data ingestion, feature engineering, serving, monitoring, retraining — wired together and actually running?

    That's what this project builds. The model itself is deliberately not the point (more on why below). The system is.

    Approach

    Data. Everything trains on Synthea synthetic patients — ~1,180 FHIR R4 bundles, each a full longitudinal history (encounters, conditions, observations, medications, procedures, claims). Synthetic by construction: no PHI, no data-use agreement, fully reproducible. The label is 30-day readmission after inpatient discharge: 2,108 discharges from 283 patients, 33.5% positive.

    Features. 26 features engineered directly from FHIR resources with a single code path used in both training and serving (no train-serve skew): demographics, length of stay, utilization history (prior inpatient/ED/ambulatory counts, days since last discharge), chronic-condition flags, and the latest pre-discharge vitals and labs (BMI, blood pressure, HbA1c, glucose, creatinine, eGFR, sodium, potassium).

    Model. LightGBM against a logistic-regression baseline, validated with patient-grouped splits — all of a patient's discharges land on one side of the split, so the model can't memorize frequent flyers. A 57-patient holdout is frozen for every future champion/challenger comparison.

    The system around it:

    FHIR bundles → feature pipeline → LightGBM champion → FastAPI + Docker (production serving)
                                                        ↘ static HF Space (in-browser ONNX demo)
Weekly: fresh synthetic cohort → retrain challenger → promote only on frozen-holdout gate
Weekly: drift check (PSI of served prediction distribution vs training baseline)

    The demo Space is a fun constraint: Hugging Face's free tier only allows static sites, so the champion is exported to ONNX and scored with ONNX Runtime Web directly in the visitor's browser. The FastAPI service and Dockerfile stay in the repo as the production serving design.

    Results

    LightGBM (champion v2026-10)0.930.80

    Top features: days since last discharge, medication count, lifetime inpatient stays, eGFR, sodium — utilization history dominates, as you'd expect.

    The honest read on 0.93: it's Synthea's strong patient-level autocorrelation talking, not modeling genius. Synthetic patients are generated by disease modules with consistent behavior, so "frequent flyers keep flying" is nearly deterministic. This is a systems demo, not a clinical result, and the model is not validated for clinical use.

    The more interesting result is the system working as designed. The first weekly run trained a challenger (AUC 0.917) that failed the promotion gate (needed ≥ 0.921) — so the champion stood, and the run was recorded. A retraining loop that says "no" is doing its job.

    Takeaways

    • The boring parts are the engineering. Frozen holdouts, identical feature code in training and serving, promotion gates — none of it is glamorous, all of it is what separates a demo from a system.
    • Build the check that catches your own bugs. The ONNX export has a parity check against the native model. It caught a real scoring bug: I'd median-imputed missing values for the browser demo, but the champion was trained with LightGBM's native NaN handling — one patient scored 30.5% imputed vs 0.2% from the actual model. The check existed to catch conversion issues; it caught a conceptual one instead.
    • Synthetic data unlocks the whole loop. No PHI meant I could build ingestion, serving, monitoring, and retraining end-to-end and run it on a schedule — the parts that are usually hand-waved in portfolio projects.
    • Constraints produce design. "Static hosting only" led to in-browser inference, which turned out to be a better demo than an API: visitors interact with the model instead of reading about it, and no patient data — even synthetic — ever leaves their machine.

    Caveats

    • All patients are synthetic (Synthea). No real clinical data, no clinical validity — do not use for medical decisions.
    • Readmission is defined as any inpatient return within 30 days; transfers and planned returns aren't separately excluded.
    • The weekly "new data" is freshly generated synthetic cohorts, simulating arrivals — a stand-in for the real workflow where outcomes join prediction logs after 30 days.
